# Native app

`EddysWallet.xcodeproj` is a SwiftUI iOS/iPadOS app targeting iOS 17 and device families 1 and 2. The built app bundle identifier is `com.kunchenguid.eddieswallet`, matching the registered Apple App ID and the production Apple audience. The UI uses adaptive `horizontalSizeClass` layouts and native sheets, forms, navigation, Dynamic Type-friendly system fonts, and accessibility labels.

## Production configuration

The app has one shipped API environment. `APIConfiguration.productionBaseURL` is the explicit production base URL:

```text
https://eddieswallet.kunchenguid.com
```

There is no staging or development API configuration in this client. First-run parent sign-in may call this API to exchange a service session and check the exact Apple account for an existing wallet before setup. If the parent proceeds with ordinary free setup, `LocalWalletRepository` persists the one-child aggregate in protected, backup-excluded Core Data and is the accepted authority on that device; subsequent free-wallet reads and writes do not call or depend on the API. A successful local read also runs one apply-on-read settlement pass before publication: due chain-head occurrences of parent-created weekly schedules settle through `LocalWalletRepository.applyDueScheduledSettlements`, oldest-first, one occurrence per save, all due allowance credits before any due loan debits, at most `ScheduledSettlementPolicy.maxOccurrencesPerPass` due occurrences per schedule. A larger derived backlog stays on the parent-confirmed missed-set path. An underfunded loan installment stays `scheduled` and is retried on a later pass. Cloud wallets never auto-write from the client, and a Cloud replica stored in `LocalWalletRepository` is skipped. `WalletStore.submit` still requires parent elevation for every manual action. `APIWalletRepository` remains the compatibility implementation for legacy service wallets; `MockWalletRepository` remains available for previews and unit tests.

The optional Cloud path is wired but guarded. `EddysWalletApp` composes one `CloudAPIClient` over the keychain session and a `CloudCoordinator`, and `WalletStore` owns them:

- `CloudAPIClient` is the public `/v1` contract used by this slice: capabilities, context, transaction JWS delivery, bootstrap, changes, household import, legacy context, the legacy-to-Cloud transition, and session revoke. Capability discovery remains public: it presents a non-expired parent session when one exists so the service may scope availability, but remains anonymous without one; every other authenticated route requires a session. Field names, optionality, statuses, and the import hash order are pinned by `EddysWalletTests/Fixtures/cloud-api-contract/v1.json` and asserted in `CloudContractTests`.
- Purchase and restore controls appear only when the backend reports `cloudActivationAvailable` **and** StoreKit returns exactly the two Cloud products. Prices always come from StoreKit; the app contains no price string. An unavailable answer stays distinguishable end to end: `.productsUnavailable` carries a `CloudPlansUnavailableReason` separating the service's deliberate "no" (`notOffered`) from a failed check (`couldNotCheck` - unreadable capability answer, thrown product query, or a wrong product set), the parent card branches its wording on that reason and always offers a "Check again" retry that re-runs the whole check, and each check records its per-step outcome class (capability read, product load) in the local recovery evidence.
- The client never grants Cloud from StoreKit state. A backend-projected `active`/`billing_grace` entitlement permits first activation, while a verified Cloud household permits an existing household to be adopted on another device. If purchase returns an unknown result or throws after Apple's sheet, or if explicit restore sync throws, the client first runs passive recovery and delivers any recovered verified transaction through the same backend path without starting another purchase. Passive recovery scans the iOS 17 discovery surfaces in fallback order - current entitlements, latest transaction per Cloud product, transaction history filtered to the configured Cloud products, then subscription-status transaction fields - and delivers only verified results; unverified results are counted for the local evidence readout and never sent. `Transaction.updates` is subscribed in its own long-lived task so a never-terminating `Transaction.unfinished` sequence cannot block it. A successful explicit Restore whose immediate sweep finds nothing usable runs exactly one bounded delayed rescan (30 seconds later, with no polling loop and no repeated sync); if both sweeps still find no usable Cloud transaction, the parent sees the truthful App Store/client failure instead of a silent unchanged screen. A delivered transaction whose backend projection is expired, refunded, revoked, or in billing retry renders that real state, never a generic server rejection. Concurrent observations of the same signed transaction coalesce into one in-flight backend delivery, and one sweep delivers at most one transaction. With no verified entitlement, the failure remains an App Store/client error; only a genuine backend rejection is presented as a server rejection. A StoreKit transaction is finished only after the projected entitlement grants Cloud. A 202 or unreadable response remains pending, while a backend 4xx or confirmed rejection is rejected without finishing.
- `CloudRecoveryEvidence` keeps collecting local aggregate recovery outcomes in every build: per-surface verified Cloud and unverified counts (or empty), the immediate-versus-delayed scan phase, the explicit-Restore sync outcome class, the last plan-availability check's per-step outcome classes (capability read: `permitted` / `notPermitted` / `unreadable`; product load: `loaded` / `storeReturnedNone` / `productSetMismatch` / `networkFailure`), the last delivery outcome class, and the app version/build. It can hold no signed payload, receipt, transaction or account identifier, session value, correlation id, wallet data, or raw StoreKit error; it never persists and never leaves the device. Its readout (`CloudRecoveryEvidenceView`) is no longer a shipped screen: Cloud/client sync diagnosis is finished, so the view compiles only into Debug and Parent > Cloud offers no route into it - see the diagnostics seam below.
- First-run sign-in on a device with no wallet exchanges one service session from the same Apple proof (`POST /v1/auth/apple`) and reads `GET /v1/cloud/legacy-context` for that exact parent before choosing setup. `CloudLegacyContext.discovery` is the single classification every first-run decision is taken from: no household keeps ordinary local-first setup; `local_detached` and an unreadable authority offer no server recovery; an already-`cloud` household is adopted straight through context and bootstrap and never through the transition; a `legacy_service` household under an active entitlement is offered as a deliberate choice on `ExistingWalletView`. Declining sends nothing. Discovery failure, offline, or an unavailable service degrade to local-first setup with a truthful notice and a `Check again` action, never to an automatic transition or a dead end.
- Accepting is one logical user action: `POST /v1/cloud/legacy-activate` with `If-Match` at the discovered revision, no body, and one idempotency key that is minted per acceptance and reused only for retries of that same acceptance. Refusals are typed (`CloudLegacyActivationRefusal`), roll back completely on the service, and are shown as what they are; a blocker that may clear replays the same protected key, a stale or unusable acceptance re-runs discovery so the parent chooses again with a new key, and a blocker that will not clear offers no retry at all. A recovered device enters the existing wallet through the ordinary Cloud bootstrap with no re-setup, no duplicate household, and no balance reinterpretation; its parent PIN is chosen at the Parent door like any other missing-PIN device.
- A device still on `APIWalletRepository` converges by itself: when its own wallet snapshot reports `family.authority == "cloud"` it switches through the same context and bootstrap path a second device uses. It never converges while one of its own legacy writes is unresolved, and a write the service refused after the transition stays visible across the switch. There is no dual-write window and no second state owner.
- Activation uploads the complete local household once through `CloudImportManifestBuilder` with a reserved operation id, stable idempotency key, and a canonical `aggregateSha256` that matches the service's accepted aggregate byte for byte. Manifest capture holds an exclusive local transition lease: it waits for any active scheduled-settlement pass, blocks all local mutations through upload resolution, preserves that block across relaunch for timeouts, unreadable responses, 408/5xx answers, and `COMMAND_IN_PROGRESS`, and releases it after a definitive rejection. Exact retries therefore cannot upload changed facts; an older local aggregate with an incomplete import operation is normalized to the same unresolved state when loaded. A launch-time fresh context read also resolves a persisted import lease when the entitlement later becomes inactive: a same-lineage Cloud household is adopted, while a confirmed missing or conflicting household releases the unchanged free local wallet. The manifest carries every weekly allowance plan: a live plan has a durable, complete next-occurrence ID and due date, while an exhausted plan has neither. A missing plan omits `allowanceRule` entirely, using the same digest-compatible pattern as `loanOccurrences`. Locally the weekly plan stores the same occurrence chain a scheduled loan stores: at most one `scheduled` row, none when exhausted or when Cloud has not named a complete service head, and each recorded row names the accepted entry that settled it. Import still hashes only the chain head on `allowanceRule`; `/v1/cloud/bootstrap` and `/v1/cloud/changes` may carry `allowanceOccurrences` the way they carry `loanOccurrences`. A second device for the same parent bootstraps instead of uploading.
- After activation, `CloudWalletRepository` keeps the service as the accepted authority and the protected local aggregate as an offline replica. Runtime money, allowance, and child-profile writes send the replica revision as `If-Match`, then reread `/v1/cloud/changes`; only a stable server entry id or accepted revision can prove observation. Parent reads load `/v1/allowance-rule` at that confirmed revision when the accepted replica has an active allowance plan, because a live changes replica may still omit `allowanceOccurrences` and therefore the service-owned next occurrence. A live rule returned by that route is cached even when no matching replica plan exists, but ordinary presentation overlays the replica only for a complete matching head or an exhausted schedule; an incomplete or unmatched head leaves the accepted replica projection unchanged. A failed or overtaken schedule read discards the in-memory overlay. **Pay out missed allowance** freezes the set the parent confirmed and submits each past-due occurrence separately through the existing allowance endpoint. Each accepted prefix is durable, today's occurrence is excluded, and any unresolved write or required review stops the sequence before another command. The repository persists at most one exact unresolved request before transport starts, including its body, revision, and idempotency key. Response loss, timeout, malformed success, relaunch, and reconnect therefore replay the same request instead of creating a second command. New controls and authority handoffs stay blocked until that request is observed or explicitly rejected.
- A persisted or known-offline Cloud replica stays readable but cannot start a mutation until a successful server read confirms its revision. If connectivity disappears during a request, the parent sees **Waiting to sync** without a balance change. A server-accepted write whose reread fails has distinct accepted-and-waiting copy and is never rendered as **Not recorded**. Explicit mutation rejections leave the accepted replica unchanged; a revision conflict asks the parent to refresh and review before retrying. Authentication failures during reconciliation stay unresolved because they cannot disprove an earlier commit.
- Cloud write readiness is derived, never stored: `CloudWalletRepository.isReadyForRuntimeMutations` is true exactly when `confirmedRevision` matches the accepted replica's revision. An applied read sets that confirmation, a benign overtaken answer leaves it alone, and a settled read with a meaningful failure - an unreachable authority, an unreadable body, a wrong lineage, or a conflict - withdraws it. A read that observed nothing (a cancelled attempt or a read refused by the Cloud-to-local hand-off lease) changes nothing, which is the same rule `APIWalletRepository` already applies before marking its cached child view stale; getting it wrong was the 0.1.14 parent-area defect. Write safety does not rest on readiness alone: the write still carries the confirmed revision as `If-Match`, so a replica that fell behind is refused by the service and routed into review.
- A loan may carry a creation-time installment plan, and everything a parent sees about it is derived on the device. `Loan.schedule` holds the durable plan - cadence, named payment amount, anchor date - plus the occurrence chain, of which at most one is ever `scheduled`. `Loan.missedInstallments` walks that chain forward from the one waiting occurrence, stops strictly before today, and carries the balance down as it goes, so each payment is `min(named amount, what is left)`, the last one caps at the remaining balance, and the owed total can never exceed the outstanding loan however long a plan has been abandoned. `nextCurrentOrFutureInstallment` is the reminder and is deliberately separate from the chain head, which may be a past day while a parent catches up. Cloud needs no extra service read for any of this: `/v1/cloud/bootstrap` and `/v1/cloud/changes` already carry `loans[].schedule` and the wallet's `loanOccurrences`, which is exactly the durable pair the replica may hold - neither embeds "today". **Pay missed payments** freezes the set the parent confirmed and records each past-due occurrence separately through `POST /v1/loans/:loanId/occurrences/:occurrenceId/record`, whose body deliberately names no amount because the service decides it. Recording the earliest occurrence is what makes the next past-due one appear, so an overdue span is settled by walking that chain; each accepted payment is durable, today's payment is excluded, and any unresolved write or required review stops the sequence before another command. A free-amount repayment that clears the balance retires the pending occurrence, so a settled loan never leaves a reminder standing. A loan created without a plan has no schedule, shows no reminder, and keeps the one-shot repayment path unchanged.

- One derivation owns the parent write guard. `WalletStore.isSyncedWithCloud` is the whole evidence a "syncing with Cloud" claim needs and exactly the evidence `canStartParentMutation` needs, so the green Cloud line can never appear beside a disabled money control; `WalletStore.parentMutationBlock` names which guard is holding, and `ParentMutationBlock` owns that case's parent-facing reason and the label of the control that clears it. Every block therefore states its own reason and carries its own way out on the block itself - `clearParentMutationBlock` reads the latest wallet, and a plan that is not active points at the Cloud plan surface instead. A definitive 409 or 428 refusal of a money, allowance, or child-profile change raises a `CloudReviewPending` whose revision floor is anchored to that refused mutation: for a 409, the greater of the service's current revision and one past the refused expected revision; for a 428, the refused expected revision. Floors only rise. Both the block's recovery and **Got it** use one clearance boundary: the repository must be ready, its monotonic accepted revision must be at or past the floor, and `authorityState.revision` must prove that the store has published a Cloud balance at or past the floor. The checks compare values, never read timing or identity, so a read silenced behind a newer pull cannot clear review while the screen still shows the pre-conflict balance. A read that fails, lands below the floor, or has not published leaves the block and its reason exactly as they were, with the same control still offered.
- Wallet reads overlap: the store reads at launch, the kid home reads when it appears, returning to the foreground reads again, leaving the Parent area reads again, and pull-to-refresh reads on demand. Every read is a task the store itself owns: a caller that stops waiting - SwiftUI ends the task behind every `.refreshable` - cancels only its own waiting, never the read or its publication, so no gesture can kill the newest read and leave an older answer silenced with no publisher left. Only the newest read of the current generation publishes, through the single guard in `WalletStore.performRead`, so a slow read can never land last and overwrite what a later read already showed; an older read's data still advances the repository, and the newest read republishes repository state. On a free local wallet the publishing read also awaits `applyDueScheduledSettlements` and then re-checks that newest-read identity, so the kid home publishes the settled balance. The kid home's connection wording therefore reflects the newest read that actually reached its authority, never a stale attempt finishing underneath it; a read that genuinely cannot reach its authority still keeps the last accepted wallet on screen and says so.
- Cloud server reads are serialized: `CloudWalletRepository` runs one at a time, in request order, so a settling read is by construction the newest observation this process has and no generation or start-order bookkeeping arbitrates between in-flight answers - none are ever in flight together. The one arbitration rule compares values, not timings: an answer older than the accepted replica is one this device has already overtaken - the service may answer a fresh request from a lagging snapshot - and it is a benign no-op that returns the newer accepted wallet unchanged: never an error, never a connection claim, and never a reason to retract the confirmation a current read already earned. An answer at or past the accepted revision applies and confirms. A regression is therefore unrepresentable whatever order answers arrive in, and `LocalWalletRepository.applyCloudReplica`'s monotonic accepted-revision guard remains the last defence beneath it.
- A failed request keeps the failure it actually hit. Every error the transport throws becomes `WalletAPIError.transportFailure` carrying a `TransportDiagnostic` instead of one blanket "the network is unavailable". The kid-home refresh path, which reads `GET /v1/child-view` for legacy service authority and `GET /v1/cloud/changes` for Cloud authority, fully applies the transport-failure contract: `WalletStore.connection` publishes `deviceOffline` only when the device itself reported no usable network, `serviceUnreachable` for a timeout, TLS, DNS, refused, or dropped connection on a device that is otherwise online, and no change at all for a cancelled attempt, which observed nothing. `KidCopy.statusBanner` owns the three kid-facing wordings and is a total function of what the newest read proved: offline only for `deviceOffline`, hard to reach only for `serviceUnreachable`, and "couldn't update" for a wallet that answered but whose answer could not be used - an unreadable body or a failure the service itself reported. A family on working WiFi is never told they are offline, and a wallet that answered is never called hard to reach. Mutation-completion paths in `submit`, `setAllowance`, and `updateChildProfile` do not yet guarantee an observable kid status when an outcome carries a failed HTTP answer; this known inconsistency is deferred to a tracked follow-up. The diagnostic keeps only non-identifying shape - failure class, raw code, whether an underlying error existed, a normalised route template, HTTP status when a response arrived, elapsed time, and a timestamp - and can hold no account, session, wallet, URL, query, body, or raw error content. `ConnectionDetailsView` renders exactly `TransportDiagnostic.displayRows` behind the parent PIN, offered only after something failed, and its copy action shares those same rows; `TransportDiagnosticTests` drives representative thrown errors end to end and pins both the honest classification and that shape.
- Signing out of a Cloud device or continuing locally after terminal entitlement first catches up with Cloud and refuses the handoff while any mutation is unresolved. The mirrored wallet becomes mutable local authority only after a current reread. When the replica has an allowance plan, handoff requires a complete matching service-owned head or an exhausted schedule; an incomplete or unmatched overlay refuses the handoff instead of making a stale replica head locally payable. The validated overlay is written onto the replica in the same save as the authority change, so already-paid weeks cannot reappear as missed; the destructive erase warning stays only for local-only wallets.

The checked-in StoreKit configuration is a Debug/Test scheme input for Xcode launches only: it is selected by the shared scheme's Test and Launch actions and is deliberately **not** a member of the app target's Resources, so it never ships. Under `xcodebuild` (including CI), StoreKit ignores the scheme's `StoreKitConfigurationFileReference` and resolves the live App Store sandbox catalog over the network. `CloudDiagnosticsView` is a Debug-only surface that renders what StoreKit resolved (`storekit-product-*`, `storekit-price-*`); `testDebugStoreKitDiagnosticsProvesTheExactCloudProductsAndPrices` drives it in a real Debug app run to prove the live response, while `CloudStoreConfigurationTests` separately keeps the checked-in configuration aligned with the accepted product contract. Neither of those two surfaces ships - the one shipped readout is the parent-only `ConnectionDetailsView` described above - and neither has a public entry point even in Debug: `DebugLaunchScenario.showsDiagnosticsEntryPoints` puts both links behind `EW_UITEST_DIAGNOSTICS=1`, so an ordinary Debug run shows exactly the parent-facing Cloud section a TestFlight build shows, and `testParentCloudSectionOffersNoPathIntoDiagnostics` keeps it that way. Cloud activation remains under development and is not proven end to end. See [`docs/app-store-configuration.md`](../docs/app-store-configuration.md) for the authoritative live StoreKit, TestFlight, and backend evidence boundary.

When first-run discovery, a legacy wallet, or a Cloud wallet needs a session, its opaque token is stored with `KeychainSessionStore` using the `com.kunchenguid.eddieswallet.session` service and an after-first-unlock, this-device-only keychain item. First-run discovery may therefore leave a service session on a device whose parent continues with free setup, but free-wallet reads and writes never use it. The parent PIN uses `com.kunchenguid.eddieswallet.parent-pin`. The owning parent's opaque Apple user identifier is stored under `com.kunchenguid.eddieswallet.parent-apple-user`; it contains no name, email, or credential and exists only so forgotten-PIN recovery and service-session renewal can verify that a fresh Sign in with Apple presents the same parent account. A different Apple user identifier fails with `WalletAPIError.identityMismatch` before any optional service-session exchange. Identity tokens and Apple private keys are not stored. On upgrade, each keychain store attempts a narrowly scoped in-place service rename from its prior service before reading or writing; this uses `SecItemUpdate` and never logs or copies secret data. If the operating system does not permit access to the prior item after the App ID change, the user must sign in again or set a new PIN. For service-authoritative wallets, a cached accepted snapshot is used for offline display and is marked stale when it cannot be refreshed; an unresolved command is shown as **Waiting to sync** and does not change the accepted balance.

## Local development and tests

Every command-line and CI simulator build and test goes through `test/sim.sh`, which owns
the whole device lifecycle: it reaps devices orphaned by earlier dead runs, creates exactly
one run-scoped device in the default CoreSimulator set, boots it headlessly, substitutes
`{{UDID}}` into the command, and shuts down and deletes that device and its XCTest clone on
success, failure, timeout, EXIT, INT, and TERM. Deleting the device takes the app container
with it, so nothing accumulates between runs. The wrapper only ever touches devices carrying
its run-scoped name prefix, so simulators you opened yourself for the manual Xcode sequences
below are never disturbed. `test/check-sim-usage.sh` exercises the public wrapper boundary,
and `test/sim-lib-test.sh` proves the reaping and teardown decisions, both without booting a
simulator. CI routes its device-backed simulator builds and tests through the wrapper.

```sh
./test/sim.sh -- xcodebuild test \
  -project EddysWallet.xcodeproj -scheme EddysWallet \
  -destination 'platform=iOS Simulator,id={{UDID}}'
```

Unit and contract-style transport tests cover Apple session exchange, bearer sessions, revision and idempotency headers, successful Cloud writes, response loss after acceptance, timeout, malformed response, exact retry, concurrent identical actions, 409 conflicts, entry-id and accepted-revision observation, failed rereads, non-money writes, relaunch, offline replicas, and authority handoffs. Native UI tests use the Debug-only `EW_UITEST_SCENARIO` launch seam in `DebugScenarios.swift` to exercise synthetic signed-in states and capture Recorded, accepted-waiting, unresolved-waiting, Not recorded, and reconnect surfaces; that seam is excluded from Release builds. Normal tests inject fakes and in-memory stores and never call production. `CloudVerticalSliceTests.testSyntheticAppClientToBackendToPostgreSQLWrite` is an opt-in external-boundary test that runs only when its four `EW_CLOUD_E2E_*` loopback variables are supplied and a separately maintained synthetic service and disposable database are already running.

## Apple Sign In signing prerequisite

The source project declares the Sign in with Apple capability and `EddysWallet/EddysWallet.entitlements` contains `com.apple.developer.applesignin`. That source configuration does not guarantee that a locally built app is entitled: the captain must be signed into Xcode with the Apple Development team that owns the explicit App ID `com.kunchenguid.eddieswallet`, with Sign in with Apple enabled and a usable Apple Development certificate/account setup. This is an external prerequisite and cannot be supplied by this public repository. Do not commit a Team ID, provisioning profile, certificate, private key, or Apple account data.

After building, inspect the signed bundle rather than only the project settings:

```sh
rm -rf .derived
./test/sim.sh -- xcodebuild build \
  -project EddysWallet.xcodeproj -scheme EddysWallet \
  -configuration Debug \
  -destination 'platform=iOS Simulator,id={{UDID}}' \
  -derivedDataPath .derived
codesign -d --entitlements :- \
  .derived/Build/Products/Debug-iphonesimulator/EddysWallet.app 2>&1
```

The output must contain `com.apple.developer.applesignin` with the `Default` value. If it is absent, the bundle is locally/ad hoc signed without the capability and the Apple Development signing setup must be fixed before testing native Apple authorization. A correctly entitled bundle is required but does not by itself prove that an Apple-side 401 or `AKAuthenticationError -7026` has been resolved.

## Manual simulator sequences

Except for the narrow live boundary recorded in [`docs/app-store-configuration.md`](../docs/app-store-configuration.md), these full sequences have **not** been run, so live end-to-end success must not be claimed.

### Free one-device wallet

1. Complete the Apple Development signing prerequisite above. In Apple Developer, confirm the explicit App ID `com.kunchenguid.eddieswallet` has Sign in with Apple enabled. Do not commit the Team ID.
2. Build and run the `EddysWallet` scheme from Xcode on an iOS 17+ simulator with the app's registered bundle identifier. The shared Debug scheme uses the checked-in StoreKit test configuration when Xcode launches the app. Sign in with Apple using the simulator's Apple ID/test account.
3. Confirm the app reaches the parent setup form. Enter a nickname and a four-digit parent PIN, create the free local wallet, and confirm setup completes without requiring the service. The PIN is stored only in the platform keychain and gates the Parent area locally. Setup completion must land in the Parent area with the first-actions handoff and a `Show <child>'s wallet` exit.
4. Confirm the Parent area shows the accepted virtual balance and the fixed notice: “Virtual practice only. These dollars are pretend, cannot be redeemed, and never move real money.”
5. Create a loan with a weekly payment plan whose named payment is larger than the principal. Confirm the Parent area shows **Loan payments**, puts **Next payment** one week after creation, displays the actual capped principal rather than the larger named amount, and shows no missed-payment action before that date. Pay the loan in full through **Pay toward loan** and confirm the reminder retires. Then create and settle a loan with **No plan**, confirming it never shows the **Loan payments** card.
6. Set a weekly allowance rule whose first occurrence is today. Leave the Parent area, pull to refresh, and confirm today's allowance is already a recorded activity without a new parent payout. Then set a weekly rule whose first occurrence is exactly four weeks before today. Confirm the Parent area still lists the four missed weeks under **Missed allowance** (the derived backlog is larger than the auto-settle cap), shows the count and **Owed total**, and keeps **Next allowance** on the earliest current or future date. Use **Pay out missed allowance**, verify the confirmation excludes today's allowance, then **Pay out all** and confirm each missed week becomes a separate accepted activity entry. Use **Pay out allowance** for today's ordinary occurrence. Then record a deposit, an allowed withdrawal, a loan, a partial repayment, and a full repayment. For every action, verify the review screen, `Recorded` result, activity row, exact minor-unit balance, and the loan's remaining amount.
7. Inside the Parent area's Settings section, open `Edit child profile`, edit the child nickname, and confirm the child-named balance and kid home both show the locally saved name after exit. Leave the Parent area with `Done` and confirm the kid home is read-only, has no parent money actions or sign-out, and keeps activity and loan details readable. Relaunch and background or foreground the app and confirm it always returns to the kid home; confirm re-entering the Parent area requires the PIN at the Parent door.
8. Turn off network access and confirm the free wallet remains fully usable: reads and parent-recorded actions continue against protected local authority, actions appear as `Recorded`, and no `Waiting to sync` or service-session state is introduced.
9. Verify the forgotten-PIN path: `Forgot PIN?` on the gate requires the owning parent's Apple account and then allows setting a new PIN without touching wallet data.

### Legacy service-wallet compatibility

This separate operator sequence applies only to an upgrade that already has the legacy configured-wallet marker, cached child snapshot, and service session. It does not describe a newly created free wallet or prove optional Cloud activation.

1. The service operator configures the single production host and TLS for `https://eddieswallet.kunchenguid.com`, sets the backend Apple audience to `com.kunchenguid.eddieswallet`, and verifies `GET https://eddieswallet.kunchenguid.com/healthz` is healthy.
2. Install this build over the configured legacy app without clearing its app data. Confirm startup retains `APIWalletRepository` authority and the kid home refreshes through `/v1/child-view` rather than converting the cached snapshot into local authority.
3. Turn off network access, refresh, and confirm the kid home keeps the last accepted snapshot with kid-worded offline copy and a stale `Last updated` label. Inside the Parent area, submit a command and verify `Waiting to sync` without an accepted-balance change. Restore network, refresh, and verify the service accepts it once using its idempotency key or rejects it as `Not recorded` without changing accepted money.
4. Expire or revoke the service session, make a request, and confirm the app keeps only the cached read-only kid view with the note that a parent needs to sign in again, then requires the owning parent's fresh Sign in with Apple before any parent surface appears.
5. Record the result as an operator test report. Do not mark this repository or pull request as live end-to-end verified until the production endpoint and real-account simulator run are complete.

Remaining operator configuration is intentionally outside this repository: the Apple Development account/certificate and capability setup described above, DNS and TLS for `eddieswallet.kunchenguid.com`, backend `APPLE_AUDIENCES=com.kunchenguid.eddieswallet`, and the production service's backups, exports, and deployment health checks. No Team ID, token, credential, or private key belongs in Git.
